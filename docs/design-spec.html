00

The thesis

What is actually new here

Generative models of Minecraft — Dream-Cubed, Oasis, the GDMC lineage — condition on shape: terrain, style, silhouette, a prompt describing appearance. Success is judged by whether a human thinks it looks right. That works for landscapes, where "looks right" is the whole objective.

Redstone breaks that. A circuit that looks like a circuit and does nothing is worthless, and the difference between working and broken is often one block. So the objective has to change: condition generation on function, and let a simulator decide whether the sample was any good.

That single change unlocks three things nobody in the voxel-generation space currently has:

  • A dense, free, non-human reward signal. No annotators, no aesthetic preference model. Every sample gets an exact pass/fail plus continuous scores for latency and footprint.
  • Unlimited perfectly-labeled training data. Compose known-good gate primitives into random graphs, derive the label from the graph. No scraped schematics, no licensing ambiguity, no noisy captions.
  • A self-improvement loop with a hard floor. Sample, simulate, keep only what verifies, retrain on that. Quality can only go up, and you can plot it.
One-line pitch

A text-conditioned discrete diffusion model over Minecraft block states, trained on procedurally-generated logic circuits, and fine-tuned exclusively on its own samples that pass a headless redstone simulator.

Repo name candidates

redstone-whisperer is memorable but soft for a systems repo. Stronger: dustc (the dust compiler), ticksmith, gfx15 (a signal-strength pun), verilogic. Recommendation: dustc as the package name, "Redstone Whisperer" as the project title in the README hero.

02

Representation

Grid geometry, block-state vocabulary, token order

Grid geometry

Redstone is overwhelmingly planar. Circuits spread in x/z and use y only for torch towers, dust-over-block runs, and the occasional two-level crossing. A cube is the wrong shape; a slab is right.

Propertyv1 valueRationale
Grid dims (x, y, z)16 × 6 × 161536 cells. Fits the vast majority of ≤6-gate combinational circuits with routing slack.
Origin conventiony=0 is the substrateLayer 0 is always solid or air; dust lives on y=1. Removes an entire class of "floating dust" invalid samples.
Token ordery → z → x rasterLayer-major. Keeps a full planar layer contiguous in the sequence so local attention sees a whole slice.
I/O portsfixed edge slotsInputs on the x=0 face, outputs on x=15. Fixing port positions removes a huge nuisance degree of freedom in v1; free-placement is a v2 ablation.
Sequence length1536 + 32 prefixPrefix carries the encoded spec (§05).

Block-state vocabulary

One token per fully-resolved block state, not per block type. A repeater facing north with delay 3 is a different token from one facing north with delay 1, because they behave differently and the model must not have to infer state from context. Dust connection shape is excluded — it is derivable from neighbors, so including it would let the model emit self-contradictory grids.

v1 vocabulary: 48 tokens. That is astonishingly small — smaller than a DNA k-mer vocabulary — which is exactly why a 25M-parameter model is the right size and why this trains on one consumer GPU.

Design note

Resist the urge to expand the vocabulary early. Pistons, dispensers, droppers and slime blocks all bring in quasi-connectivity — the notorious Java-edition bug where a block "senses" power diagonally below-adjacent. Modeling QC correctly triples simulator complexity and makes your golden tests version-dependent. Ship combinational logic first.

03

The simulator

The component the whole project's credibility rests on

This is not a Minecraft reimplementation. It is a deterministic model of a documented subset of redstone, plus a harness that proves the subset matches the real game. Being explicit about that boundary is what separates a serious repo from a toy.

Tick semantics

RuleBehavior
time base1 redstone tick = 2 game ticks = 0.1 s. Simulator steps in game ticks; latency reported in redstone ticks.
dust propagationInstantaneous within a tick. Strength = max(neighbor) − 1, floor 0. Solved by multi-source BFS from all emitters, not by iteration — this is both faster and exactly correct.
dust range15 blocks from a strength-15 source. Enforced by decay, not by a special case.
torchOutput = ¬(attached block powered), with 1 redstone tick delay. Powers the block above it and dust adjacent to it.
repeaterRestores to 15, directional, delay 1–4 rt, blocks reverse signal. Locking by side-input repeaters: implement, it is cheap and common.
comparator1 rt delay. Compare: out = rear if rear > max(sides) else 0. Subtract: out = max(0, rear − max(sides)).
block powerTwo-tier: strongly powered (by a torch below, repeater facing into it) vs. weakly powered (by dust pointing into it). Only strong power re-emits into adjacent dust. Getting this distinction wrong is the #1 source of simulator/game divergence.
update orderDeterministic: torches and repeaters latch their inputs at tick boundary, then all update simultaneously. Real Java uses a quasi-random block-update order; document that as a known divergence and reject any circuit whose behavior depends on it.
torch burnoutDetect (>8 toggles in 60 game ticks) and reject the circuit rather than simulate the burnout. A design that burns out is a bad design.
oscillationHash the full state each tick into a rolling set. Repeat state = settled. Cycle of period >1 = oscillating → UNSTABLE, not FAIL. Distinguish these in your metrics; they mean different things about the model.

Evaluation contract

// the single function everything else is defined against
fn evaluate(grid: &Grid, spec: &Spec) -> Verdict

enum Verdict {
    Pass  { latency_rt: u8, blocks: u16, bbox: (u8,u8,u8) },
    Fail  { // exact row-level diagnosis, for the replay buffer
            mismatched_rows: Vec<(Inputs, Observed, Expected)> },
    Unstable { period_ticks: u8 },
    Malformed { // caught before simulation, cheap
            reason: FloatingDust | PortViolation | Overlap | Burnout },
}

Run every input combination to steady state (cap: 200 game ticks) and compare the output port's boolean trace. For an n-input spec that is 2n runs; at n ≤ 6 that is 64 sims per candidate, and a Rust core does that in well under a millisecond. Throughput matters enormously here because §06 samples 64 candidates per spec.

Fidelity harness — do not skip this

Build a headless Minecraft server + a small Fabric mod that accepts a .schem over a socket, places it in a void world, toggles the input levers through all combinations, and reports the output lamp's state. Then run your golden test suite through both the Rust simulator and the real game and report agreement as a headline metric.

Target: 100% agreement on the golden set, ≥99.5% on 10k random generated circuits. Publishing that number is what makes the rest of the repo believable. It is also, on its own, a more rigorous artifact than most Minecraft-AI projects contain.

04

Synthetic data engine

Why you should not scrape a single schematic

Scraping community schematics gives you a few thousand unlabeled builds of wildly varying quality, with murky redistribution rights and no reliable description of what each one does. Generating them gives you millions of perfectly-labeled examples with a known difficulty distribution. This is the rare domain where synthetic data is strictly better, and saying so clearly in the README is a good look.

Spec DSL

Every example is anchored to a canonical machine-readable spec. Natural language is a view of the spec, generated afterward — never the source of truth.

spec  := inputs ident+ outputs ident+ constraint* rule+
rule  := ident = expr
expr  := ident | ¬ expr | expr (∧|∨|⊕) expr | ( expr )
        | delay( expr , int )        // int in redstone ticks
        | strength( expr , int )     // 0..15, for comparator work
constraint := latency <= int
        | footprint <= int
        | region <= int x int

// example
inputs A B C
outputs Q
latency <= 4
Q = (A ⊕ B) ∧ ¬C

Generation procedure

  1. Sample a logic DAG. Pick gate count g ~ uniform(1, 6), input count n ~ uniform(1, 4). Build a random DAG over {AND, OR, NOT, XOR, NAND, NOR} with no unused nodes.
  2. Canonicalize. Reduce to a normal form and hash it. This hash is your deduplication key and your novelty metric later — you must know whether a generated circuit is isomorphic to something in training.
  3. Place and route. A hand-written gate library (each gate as a small voxel stamp with declared input/output pins) plus a simple A*/lee-maze router on the dust layer. Randomize gate variant, orientation, and routing detour so the same spec yields many distinct valid layouts — this is the augmentation that teaches the model there is more than one answer.
  4. Verify. Run §03 on every produced layout. Discard anything that doesn't pass. Your placer will be buggy; the verifier catches it. Log the discard rate as a health metric.
  5. Paraphrase. One LLM pass per spec producing 4–8 natural-language phrasings at varied register: terse ("NAND gate"), functional ("light only turns off when both switches are on"), procedural ("invert both inputs then combine them"), and vague ("a two-switch safety interlock"). Cache these; it is a one-time cost.
  6. Difficulty stratification. Bucket by gate count and hold out entire buckets, not random samples — you want to measure extrapolation, not interpolation.
SplitGate countSizePurpose
train1–4~2.0M layoutsMain corpus. ~200k unique specs × ~10 layouts each.
val1–410kUnseen specs, seen difficulty. Standard generalization.
test-extrap5–65kHarder than anything in training. The headline number.
test-nl1–6500Human-written prompts, hand-collected. Guards against the model only understanding LLM-flavored paraphrase.
test-repair1–42kWorking circuits with 1–8 blocks corrupted. Measures inpainting (§05).
The obvious failure mode

If your placer only ever builds gates in one canonical orientation, the model learns your placer, not redstone. Aggressively randomize: mirror, rotate, insert redundant repeaters, take scenic routes, vary substrate. Then measure it — if generated circuits are >60% isomorphic to a training layout, your augmentation is too weak.

05

The model

Autoregressive baseline, discrete diffusion as the real thing

Ship two. The autoregressive model is a two-day sanity check that your data pipeline works. The diffusion model is the one that earns the repo, because masked diffusion gives you inpainting for free — and inpainting is what turns this from a demo into a tool people actually use ("my circuit is broken, fix this region").

Baseline · autoregressive

Decoder-only transformer, prefix-LM over the spec tokens then raster-order block prediction.

  • 12 layers, d_model 384, 6 heads, SwiGLU
  • RoPE on the sequence + learned 3D positional embedding added at input
  • ~25M params, seq 1568
  • Trains in a few hours on 10–12 GB VRAM

Purpose: prove the data teaches something. Expect mediocre pass rates and no inpainting. Keep it in the repo as a documented baseline.

Main · masked discrete diffusion

Absorbing-state diffusion (MaskGIT / MDLM-style) over the same token grid.

  • Bidirectional encoder, same width/depth as above
  • Forward process: independently replace tokens with MASK at rate t
  • Loss: cross-entropy on masked positions only, weighted 1/t
  • Sampling: 16–32 steps, confidence-ordered unmasking

Why it wins: order-agnostic, so any subset of the grid can be conditioning. Repair, extension, and constrained placement are the same operation.

Conditioning

  1. Canonical spec path (primary). Tokenize the DSL directly into ≤32 prefix tokens with its own small vocabulary. Exact, cheap, and what the verifier loop uses internally.
  2. Natural language path. A frozen sentence encoder (MiniLM-class, ~22M params, runs on CPU) → linear projection → 8 prefix tokens. Frozen keeps VRAM free for the generator and stops the text tower from overfitting your paraphrase style.
  3. Classifier-free guidance. Drop the conditioning 10% of the time during training; at sampling, guidance scale 1.5–3.0. On discrete diffusion this is a logit-space interpolation. Expect this to be one of your largest single wins — worth an ablation figure.

Loss weighting — the air problem

85% of tokens are air. Unweighted cross-entropy will happily converge to a model that emits empty grids and reports excellent loss. Mitigations, in order of preference:

  • Inverse-frequency class weights, clipped at 10×, on the non-air vocabulary.
  • Report per-class accuracy and functional pass rate in every eval. Never let aggregate token accuracy be the headline — it will read ~97% while the model produces nothing that works.
  • Optional and worth trying: crop each training grid to its occupied bounding box + 1 block of padding, and predict the bbox dims as part of the prefix. Cuts sequence length ~4× and removes most of the air.
Structural priors worth trying (each a clean ablation)

Layer-factored attention: alternate blocks attending within a y-layer and across layers at fixed (x,z). Cheaper than full attention over 1536 tokens and matches the geometry.
Legality masking at sample time: zero the logits of block states that are physically impossible at that position (dust with no support below, lever off the input face). Free correctness, no training cost.
Signal-strength auxiliary head: predict the simulator's steady-state power value at each cell as a second output. Forces the representation to encode propagation rather than texture. This is the most interesting idea in this section and I'd prioritize the ablation.

06

Verifier-guided self-improvement

The loop that makes this a research contribution

Everything up to here is competent engineering. This is the part that's new: because the verifier is exact and free, the model can be trained on its own successful output indefinitely, with a monotone quality guarantee and a curve you can plot.

for round in 1..R:
    accepted, negatives = [], []

    for spec in sample_specs(n=20_000, difficulty=curriculum[round]):
        cands  = model.sample(spec, k=64, guidance=2.0, temp=0.9)
        graded = [verifier.evaluate(c, spec) for c in cands]

        passing = [c for c,v in zip(cands,graded) if v.is_pass()]
        if passing:
            # dedupe by canonical layout hash, then keep the best few
            passing = dedupe(passing)
            passing.sort(key=lambda c: (c.blocks, c.latency_rt))
            accepted += [(spec, c) for c in passing[:4]]
        else:
            # near-misses are the most informative failures
            near = min(graded, key=lambda v: len(v.mismatched_rows))
            if len(near.mismatched_rows) == 1:
                negatives.append((spec, near))

    # the actual objective: preference over verified quality
    dataset = accepted + repair_pairs(negatives)   # see below
    model.finetune(dataset, epochs=1, lr=1e-5)

    log(round, pass_at_1=eval(val), pass_at_1=eval(test_extrap),
        mean_blocks=..., novelty=..., unstable_rate=...)

Three things that make the loop actually improve

  1. Compactness as a secondary objective. Among passing candidates, prefer fewer blocks and lower latency. This is what pushes the model past the procedural placer — the placer routes correctly but wastefully, and the loop can discover layouts the placer's heuristics can't express. This is your central empirical claim: the learned model finds circuits smaller than the compiler that generated its training data.
  2. Repair pairs from failures. A candidate failing exactly one truth-table row is usually one or two blocks from correct. Diff it against a known-good layout for the same spec and emit a masked-inpainting training example: the corrupted region masked, the correct blocks as target. Failures become supervision instead of waste.
  3. Curriculum by acceptance rate. Advance the difficulty distribution when round-level pass@1 crosses a threshold (say 0.6). Advancing too early collapses acceptance to near-zero and the loop starves; too late and it overfits easy specs. Log the acceptance rate per bucket every round — this is your main diagnostic.
Watch for diversity collapse

Self-training on filtered samples is a known mode-collapse machine. The model will find one layout per gate type and emit it forever, with a beautiful pass rate and zero novelty. Defend on three fronts: dedupe accepted samples by canonical hash before training, mix in a fixed 25% of original synthetic data every round, and make distinct-layouts-per-spec a first-class tracked metric. If it trends down, the loop is failing even while pass@1 rises.

Baselines

1 · Procedural compiler

Espresso-style two-level minimization → gate library → router. The same machinery that made your training data.

It will beat you on correctness. Say so. A compiler is correct by construction; pass@1 = 1.0 within its coverage. Your argument is not correctness — it's compactness, natural-language flexibility, repair, and layouts outside the compiler's expressible space.

2 · Frontier LLM, prompted

Give a strong general model the spec plus the grid format and ask for a schematic. Run its output through the identical verifier.

Expect a low single-digit pass rate — LLMs have essentially no spatial model of signal propagation. A clean, fairly-run comparison here is a genuinely publishable observation and the most shareable chart in the repo.

3 · Retrieval

Nearest-neighbor over training specs by embedding, return that layout verbatim.

Cheap and surprisingly strong on in-distribution specs. If your model can't clearly beat retrieval on the extrapolation split, you have not yet built a generative model of circuits.

4 · Unconditional + rejection

Sample ignoring the spec, keep whatever happens to verify.

An ablation, not a competitor. It isolates how much of your pass rate comes from conditioning versus from the verifier filtering a firehose.

The figure that will get this shared

A Pareto scatter: block count on x, latency on y, one cloud per method (compiler / retrieval / LLM / your model at rounds 1, 3, 5). Every point is a verified-correct circuit. If your round-5 cloud sits down-left of the compiler's, the project's thesis is demonstrated in a single image with no prose required.

Hardware notes

RX 6700 specifics, and why it barely matters

The RX 6700 is RDNA 2 (Navi 22, gfx1031) and is not on AMD's officially supported ROCm list — as of ROCm 7.2 that list starts at RDNA 3. It nonetheless works in practice via the gfx1030 override, and the good news is that this project is unusually forgiving of a modest GPU: a 48-token vocabulary and a 25M-parameter model is a tiny workload by 2026 standards. Your bottleneck will be the CPU-side verifier throughput in §06, not the GPU.

10

Objections

Answer these in the README before anyone asks

"Just write a compiler."

Correct — and you did, it's the baseline. A compiler needs formal input, emits one layout per spec in a style its author hardcoded, and cannot repair a build a player half-finished. The learned model takes vague natural language, produces a distribution over layouts, fills in gaps, and — per §07 — finds smaller circuits than the compiler that taught it. Those are different tools. Shipping both and comparing them is the strength, not a weakness.

"This is just synthetic data on a solved problem."

Logic synthesis is solved. Spatial logic synthesis under Minecraft's propagation rules, from natural language, with repair, is not. And the closed verifier loop is the interesting object here regardless of domain — redstone is a rare setting where the reward is exact, free, and fast, which makes it a clean testbed for verifier-guided generation generally.

"Why not use the real game as the simulator?"

Throughput. §06 needs on the order of 108 evaluations per round; a game instance does maybe 102/second. The Rust core does 106. The fidelity harness (§03) is how you get the speed without giving up ground truth.

"Won't the model just memorize gates?"

Probably, at first — which is why the novelty rate and the 5–6 gate extrapolation split are tracked from day one rather than added when a reviewer asks. If it turns out to be pure memorization, publish that: a clean negative result with this much measurement around it is more useful than most positive ones.

Three stretch goals, in order of how much they'd raise the ceiling

Sequential logic. Latches, counters, clocks, pistons. Requires quasi-connectivity in the simulator and temporal specs in the DSL. This is the natural v2 and roughly doubles the project's scope and its interest.
Live in-game copilot. Fabric mod that ghost-renders a suggested completion of whatever you're currently building, using the inpainting path. This is what would actually get players using it.
Spec inference. Invert the model: feed it a circuit, get back the DSL spec describing what it does. "Explain this contraption I found" is a feature no tool currently offers, and the verifier gives you exact labels to train it on for free.

Redstone Whisperer / dustc — design specification rev 0.3. Scope: combinational logic, 16×6×16, Java-edition semantics, no quasi-connectivity. Build the simulator first.
